# WhatsApp 어댑터

개인 WhatsApp 계정으로 동작하는 어댑터입니다(`account.kind: "user"`,
`provider.id: "whatsapp-user"`, saya 표시 이름 `WhatsApp`). 비공식
클라이언트 라이브러리 [Baileys](https://github.com/WhiskeySockets/Baileys)
(`@whiskeysockets/baileys` 6.7.24, 버전 고정)로 WhatsApp Web 의 "연결된 기기"가
됩니다.

## 먼저 읽을 것: 위험

> [!WARNING]
> **WhatsApp 은 개인 번호용 공식 API 를 제공하지 않습니다.** 비공식 클라이언트는
> WhatsApp 약관이 금지하며, **계정이 정지·차단될 수 있습니다.** 이 어댑터의 소유자가
> 이 위험을 알고 직접 결정해 넣었습니다(2026-11-16). 주 번호 대신 **보조 번호**로
> 쓰기를 권합니다. 어댑터를 쓰지 않을 때는 아래 「끄는 법」을 따르세요.

AGENTS.md 의 「Deliberately absent」(공식 API 없는 메신저의 프로토콜 재구현 금지)에
대한 예외이며, 이유와 위험은 이 문서에 둡니다. 선례는 `discord-user` 입니다.
위험을 줄이려고 이 어댑터는 다음을 지킵니다.

- 보내기를 자동으로 다시 시도하지 않습니다. 결과를 모르면 `INTERNAL` 로 답합니다.
- 끊긴 연결은 1초에서 시작해 두 배씩, 최대 60초 간격으로 다시 잇습니다.
- 로그아웃(401), 다른 Web 세션의 가로채기(440), WhatsApp 의 거절(403)이면 다시
  잇지 않고 상태만 알립니다. 재로그인을 시도하지 않습니다.
- 접속해도 "온라인" 표시를 올리지 않고(`markOnlineOnConnect: false`),
  링크 미리보기를 만들지 않습니다. 방 목록·이름 수신을 위해 연결 기기를
  `Browsers.ubuntu("Desktop")`, `syncFullHistory: true`로 등록합니다.
  Ubuntu 튜플은 6.7.24에서 `WEB_BROWSER`를 유지하므로, upstream
  [#2677](https://github.com/WhiskeySockets/Baileys/issues/2677)과
  [#2880](https://github.com/WhiskeySockets/Baileys/issues/2880)의
  WIN32/DARWIN 접속 거절 경로를 피합니다. WhatsApp이 보내는 기록만 받고,
  디스크에는 방마다 최근 50개만 보관합니다.
- 대량 동작이 없습니다. 쓰기는 serve-kit 의 쓰기 줄 하나로 한 번에 하나씩 갑니다.

## 로그인

로그인은 사람이 합니다. 자동화나 우회는 없습니다.

```sh
bun adapters/whatsapp-user/src/cli.ts login
```

터미널에 QR 코드가 뜹니다. 폰에서 **WhatsApp > 연결된 기기 > 기기 연결**로
찍으세요. 3분 안에 연결되지 않으면 끝납니다(다시 실행). 연결이 열린 뒤에도
최근 대화·연락처·메시지를 받기 위해 최대 60초 더 연결을 유지합니다.
Baileys 6.7.24가 FULL history의 `progress: 100`을 보내거나 이 마감 시간이
지나면 소켓을 닫고 `sessions/whatsapp/store.json` 저장을 끝낸 뒤 `linked`를
출력합니다. `isLatest`는 첫 history 표시라 완료 신호로 쓰지 않습니다.
RECENT 100%는 뒤따르는 FULL 수신을 끊을 수 있어 완료 신호로 쓰지 않습니다.
완료 history 뒤 같은 SDK 배치로 이어지는 연락처·그룹 변경도 받은 뒤 종료합니다.
진행률이 없거나 history가 오지 않으면 마감까지 받은 부분만 저장합니다.
마감은 전체 기록 수신을 보장하지 않습니다.
세션은 `sessions/whatsapp/` 에 저장됩니다(폴더 700,
파일 600, `sessions/` 는 git 에서 제외). 세션은 계정 비밀번호와 같으니 복사·공유하지
마세요.

## 실행

```sh
bun adapters/whatsapp-user/src/cli.ts serve
```

`login` 을 하지 않았으면 `serve` 는 시작하지 않고 안내만 출력합니다.
어댑터 디렉터리의 `bun run login`, `bun run serve` 도 같은 명령입니다.
출력은 `state: open` 같은 상태와 개수뿐입니다. 전화번호, 이름, 메시지 내용,
QR, 세션 내용은 어디에도 출력하지 않습니다(Baileys 의 로그도 끕니다).

방 목록·연락처 이름과 별칭·그룹 제목·pushName 및 방마다 최근 메시지 50개는
`sessions/whatsapp/store.json` 에 저장하고, 연결하기 전에 읽습니다.
메시지 수정·삭제와 방 삭제도 반영하며, 실행 중에는 방마다 200개까지 보관합니다.
캐시는 세션과 같은 git 제외 폴더 안에 있고 권한은 600입니다. 같은 폴더의
권한 600 임시 파일에 쓴 뒤 rename 으로 교체하며, 종료할 때 진행 중인 저장을
기다립니다. 저장 실패는 `room cache save failed` 만 출력합니다.
기존 캐시가 손상되었거나 읽을 수 없으면 빈 캐시로 덮어쓰지 않고 시작을 거절합니다.
캐시가 없는 첫 실행은 정상이며, 이미 사라진 과거 목록은 이 변경으로 되살릴 수 없습니다.
기존 링크에서 초기 history를 놓쳤다면 운영자가 서비스를 멈추고 폰에서 해당 기기를
로그아웃한 뒤, 기존 `sessions/whatsapp/`를 보관용으로 옮기고 새로 `login`합니다.
`linked` 출력까지 기다린 뒤 같은 작업 디렉터리에서 `serve`를 시작합니다.
새 `store.json`의 방 목록과 이름은 다음 연결 전에 복원됩니다.
기존 링크는 등록 때 보낸 `requireFullSync`가 바뀌지 않으므로, 빈 캐시를
채우기 위한 이번 변경의 확인은 위 재링크 절차로 합니다. 정상 캐시가 있는
계정은 재시작 시 그대로 복원하며 무조건 재링크하지 않습니다.
설정과 캐시 복원은 합성 테스트로 검증했지만, 실제 계정에서 history·연락처·
그룹이 도착하는지는 운영자가 확인해야 합니다.

| 설정 | 기본값 |
| --- | --- |
| `TSUBA_WHATSAPP_USER_HTTP_TOKEN` | `TSUBA_TOKEN` |
| `TSUBA_WHATSAPP_USER_PORT` | `8795` |
| `TSUBA_HOST` | `127.0.0.1` |

`deploy/tsuba@.service` 에서는 `whatsapp-user` 인스턴스로 실행합니다
(`systemctl enable --now tsuba@whatsapp-user`). 로그인은 서비스를 띄우기 전에,
같은 사용자로, 같은 `sessions/` 에서 한 번 해 둡니다.

## 끄는 법

- 어댑터만 끄기: `systemctl stop tsuba@whatsapp-user`(또는 프로세스에 SIGINT).
- 이 기기의 연결 끊기: 폰의 **연결된 기기**에서 이 기기를 로그아웃합니다.
  어댑터는 `logged-out` 상태가 되며 다시 잇지 않습니다.
- 완전히 지우기: 위 로그아웃 뒤 `sessions/whatsapp/` 를 삭제합니다.

## 선언한 기능과 근거

선언하지 않은 기능은 없는 것이며, 해당
라우트는 `NOT_SUPPORTED` 로 답합니다.

| 기능 | 선언 | 근거 |
| --- | --- | --- |
| `rooms.list` | — | 기록 동기화·새 메시지·연결 시 조회한 참여 그룹을 최근 활동순으로 최대 500개. **`complete` 는 항상 `false`**: WhatsApp 은 전부 보냈다고 알려 주지 않습니다 |
| `attachments.read`, `avatars.read` | — | 메시지 첨부와 선택적 방·발신자 프로필 사진을 인증된 `/media` 로 읽습니다 |
| `attachments.send` | `maxBytes: 64000000`, `captionMaxLength: 1024`, `receipt: accepted` | `/upload` 로 한 파일과 선택적 캡션·답장 인용을 보냅니다. MIME 허용 목록은 없습니다 |
| `messages.read` | `paging: before-id`, `maxLimit: 100` | **어댑터가 받은 메시지**를 방마다 최근 200개까지 메모리에서 답하며, 최근 50개는 재시작 뒤에도 유지합니다. WhatsApp 에는 방의 지난 기록을 가져오는 호출이 없습니다. `hasEarlier` 는 현재 보관한 기록 안에서의 뜻입니다 |
| `messages.stream` | `resume: none`, 이벤트 `message.edited`, `message.deleted` | 연결 중 도착한 새 메시지·수정·삭제를 그대로 전합니다. 끊겼다 이으면 놓친 것을 되짚을 커서가 없어 `resume` 은 `none` 입니다 |
| `messages.send` | `maxLength: 2048`, `receipt: accepted` | 글자 수 한도는 개인 계정에 대해 문서화되지 않았고 측정도 못 했습니다. 2048 코드포인트는 최대 4096 UTF-16 단위이며 WhatsApp 공식 Cloud API 의 본문 한도(4096)보다 작아 보수적입니다. `accepted` 는 WhatsApp 서버의 ACK를 받았다는 뜻입니다 |
| `messages.reply` | — | 어댑터가 본 메시지만 인용할 수 있습니다. 모르는 메시지에 답하면 아무것도 보내지 않고 `NOT_FOUND` |

텍스트와 첨부 모두 로컬 소켓 쓰기만 끝났을 때 성공으로 답하지 않습니다.
서버 ACK가 없거나 오류를 돌려주면 결과 미확인(`INTERNAL`)으로 답하고 HTTP
발송을 자동 재시도하지 않습니다. WhatsApp가 복호화 재시도를 요청하면 SDK는
같은 방·같은 메시지 ID로 보관된 발신 원본만 조회할 수 있습니다.

발신 메시지의 `deliveryStatus`는 확인된 `sent` → `delivered` → `read`만
나타냅니다. 그룹에서 `delivered`·`read`는 구성원 한 명 이상이 확인됐다는
뜻입니다. 어댑터는 이 상태를 저장하고, 변경되면 `message.edited`로 보냅니다.

이미지, 영상, GIF 재생 영상, 음성·음성 메모, 문서, 스티커를 첨부로 표시하며
캡션은 본문입니다. 한 번 보기 미디어는 노출하지 않습니다. 파일 바이트는
저장하지 않고, 캐시에 남은 메시지의 첨부만 요청 시 스트리밍합니다. CDN이
404/410을 반환하면 링크된 기기에 재업로드를 한 번 요청합니다. 파일을 더 이상
얻을 수 없거나 기기가 응답하지 않으면 다운로드가 실패할 수 있습니다.

업로드는 파일당 64,000,000바이트, 캡션은 1,024 코드포인트로 제한합니다.
16,000,000바이트 이하 JPEG·PNG와 MP4는 인라인으로 보내고, 그 외 형식과
더 큰 이미지는 파일명과 함께 문서로 보냅니다. 변환은 하지 않습니다.
문서에도 같은 제한을 적용합니다. 공통 업로드 경로가 파일을 통째로 메모리에
읽기 때문에 WhatsApp 앱에서 허용하는 더 큰 문서까지 받지는 않습니다.

반응, 시스템 메시지, 알 수 없는 종류는 보이지 않습니다. 방은 1:1 대화, 그룹,
LID 주소, `@bot` 대화이며 상태(status), 방송 목록, 채널(뉴스레터)은 제외합니다.

### Meta AI 봇 대화

동기화나 수신 중 확인된 `@bot` 대화는 읽기 전용으로 표시합니다. 방·연락처 이름,
인증 이름, 수신 pushName이 없으면 `Meta AI bot`으로 표시합니다. 전화번호·LID
별칭을 봇과 연결하지 않으며 발송·답장·파일 업로드는 지원하지 않습니다.

SDK가 디코딩한 지원 형식의 내용만 메시지로 기록합니다. 암호문만 도착해도 직접
봇 방은 표시하지만 메시지나 미리보기를 만들지 않습니다. 폰에서 보낸 복사본은
내 기기와 봇 수신자가 확인될 때만 해당 방에 넣습니다.

디코딩된 발신 원본에 답장 복호화용 32바이트 메시지 비밀이 있으면, 최대 500개의
원본을 권한 600의 세션 캐시에 따로 보관합니다. SDK 조회는 정확한 방 ID·메시지
ID·발신 여부가 모두 일치해야 합니다. HTTP 응답과 로그에는 비밀이나 암호문이
노출되지 않습니다.

Muse의 발신 복사본이 WASA 봉투로만 도착하면 방은 표시되지만 그 본문은 보이지
않습니다. WASA 복호화와 그룹 안의 봇은 지원하지 않으며, 실제 연결 계정에서
Muse 답장이 복호화되는지는 확인하지 않았습니다. `serve` 로그는 `msmsg-seen`,
`wasa-envelope`, `missing-secret` 같은 고정 사유를 프로세스당 종류별 한 번만
남깁니다. 식별자와 SDK 오류 문자열은 기록하지 않습니다. 받은 적 없는 방을
찾아오거나 지난 기록을 다시 요청하지 않습니다.

실계정 연결 없이 확인하려면 저장소 루트에서
`bun test ./tests/whatsapp-user-bot-rooms.test.ts`를 실행하세요. 이 테스트는
합성 Baileys 이벤트를 실제 어댑터와 인증된 `/rooms`, `/messages`, `/send`
핸들러에 통과시킵니다.

그룹 제목은 연결이 열릴 때 참여 그룹을 조회하고, 이후 그룹 추가·변경 이벤트의
`subject` 로 갱신합니다. 제목 없는 부분 변경이나 늦은 채팅 기록이 최신 subject 를
덮지 않습니다. 조회 시작은 `group metadata fetching`, 성공은
`group metadata fetched: N` 으로 구분합니다. `N = 0` 은 그 응답에서 인식한
그룹이 0개라는 뜻이며, 계정에 참여 그룹이 없다는 보장은 아닙니다.
SDK는 응답에 `groups` 노드가 없어도 빈 결과로 반환하고, 연결 `open`도
초기 history·앱 상태 동기화 완료를 뜻하지 않습니다.
조회 결과는 SDK의 `groups.update` 버퍼가 비워지기를 기다리지 않고 직접 저장소에
반영합니다. 이후 그룹 이벤트도 계속 반영하며, 0개 응답 때문에 기존 그룹을 지우거나
무조건 재조회하지 않습니다. 조회에 실패해도 기존 방과 연결을 유지하며
`group metadata unavailable` 만 남깁니다. 시작 뒤 성공·실패 로그가 아직 없으면
조회가 끝나지 않은 상태입니다. 이름·id·SDK 오류 내용은 출력하지 않습니다.

1:1 방은 연락처의 `lid`·`jid` 와 번호 공유 이벤트를 같은 사람의 별칭으로 연결합니다.
이름은 저장한 연락처 이름, 채팅 이름, 연락처 `notify`, 수신 메시지의 최신 `pushName`
순서로 고릅니다. 이름 없는 연락처 부분 변경은 이미 받은 이름을 지우지 않고,
늦게 온 옛 메시지는 최신 pushName 을 덮지 않습니다. 자기 메시지의 pushName 은
상대방 이름으로 쓰지 않으며, 별칭이 연결되어도 방 id 와 메시지 기록은 합치지 않습니다.

`/send`는 LID 방 id를 그대로 SDK에 전달하며 LID 숫자를 전화번호로 바꾸지 않습니다.
Baileys 6.7.24의 자기 LID가 기기 번호 없는 `user@lid`일 때 자기 기기 수신 주소에
도메인을 두 번 붙이는 결함은 `patches/`의 Bun 패치로 고칩니다. 설치 때 자동 적용되며
SDK 버전은 올리지 않습니다. SDK 자체의 JID 디코더로 user를 추출합니다.
자기 LID가 아직 도착하지 않았으면 SDK를 호출하기 전에 `BUSY`로 거절합니다.
명시적 수신자/암호화 키 404는 `NOT_FOUND`, 알 수 없는 쓰기 결과는 `INTERNAL`이며
자동 재전송하지 않습니다. 합성 키로 실제 Signal 암호화·복호화까지 검증했지만,
실제 WhatsApp 서버 수락이나 수신자 전달은 별도 승인 후 확인해야 합니다.

## 못 하는 것

메시지 첨부 읽기·보내기, 반응, 수정, 삭제, 읽음 표시, 입력 중 표시, 보낸 사람 사진,
정확한 안 읽음 수의 보장(WhatsApp 이 보낸 값을 그대로 쓰며 없으면 0),
캐시보다 오래된 지난 기록 불러오기. 확실히 동작을 확인하지 못한 기능은
선언하지 않았습니다.

## 방 사진

디스크 스냅샷에는 방 메타데이터만 저장하며 사진 URL·바이트·미디어 id 는 저장하지
않습니다. 사진 id 는 프로세스 안의 바이트 캐시에만 대응하므로 재시작 뒤 복원하면
깨진 id 가 됩니다. 복원한 방은 연결 전에도 이름과 메시지를 바로 보여 주되 사진
조회는 연결이 열린 뒤 시작합니다. 연결 전 상태를 5분짜리 사진 없음 결과로 캐시하지
않으며, 연결 뒤 다음 목록 조회에서 사진을 채웁니다.

`/rooms` 에 실제로 나열하는 1:1·LID·그룹 방(봇 제외)에만 Baileys 6.7.24 의
`profilePictureUrl(jid, "preview", 3000)` 를 필요할 때 호출합니다.
비공개·사진 없음·SDK/다운로드 실패는 `avatar` 를 생략하며 방 목록은 유지합니다.
실패 결과도 5분 동안 캐시하고 같은 방의 진행 중 요청은 합칩니다.
전체 SDK·다운로드 작업은 동시에 최대 4개, 캐시와 진행 중 방은 각각 최대 500개입니다.
목록 조회의 사진 작업 예산은 8초이며 이후 시작하지 않은 조회는 생략합니다.
이미 시작한 SDK 조회는 SDK 자체의 3초 제한 안에서 마칩니다(취소 API 없음).

원본 URL 은 서버 안에서만 쓰고, HTTPS `pps.whatsapp.net`,
한 단계 하위 `*.pps.whatsapp.net`, `pps.whatsapp.com` 만 허용합니다.
사용자정보·별도 포트·리디렉션은 거절하며 다운로드는 5초 제한과 취소 신호를
전달합니다. JPEG·PNG·WebP 타입과 파일 서명을 검사하고 스트림을 최대 256 KiB 까지
읽습니다. 사진은 디코딩하지 않습니다. 최대 사진 메모리는 500 × 256 KiB(125 MiB),
진행 중 다운로드는 별도로 최대 4개입니다.

목록에서 새 사진을 찾을 때 미리보기 바이트를 메모리에 스냅샷으로 잡고 타입과 바이트의
SHA-256 으로 `wa-room-v1-…` id 를 만듭니다. URL 이 같아도 사진이 바뀌면 다음 갱신에서
id 가 바뀌며, URL 만 바뀌고 사진은 같으면 id 를 유지합니다. `/media` 는 인증 뒤 이
스냅샷만 serve-kit 의 CSP·nosniff·private 캐시 헤더로 답합니다. 클라이언트 id 로
원격 URL 을 가져오는 경로는 없습니다. 만료·교체·퇴출·재시작된 id 는 `NOT_FOUND` 일 수
있으며 같은 id 를 다른 바이트로 재사용하지 않습니다. 전화번호·이름·URL·오류·세션·토큰을
로그로 남기지 않습니다.
